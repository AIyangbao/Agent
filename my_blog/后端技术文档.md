## 1. 概述

基于 **FastAPI + SQLAlchemy 2.0 (Async) + MySQL + Redis** 的异步 API 服务，负责博客增删改查、用户认证、评论、音乐、RSS/sitemap，以及两个亮点功能：**RAG 博客问答** 与 **Tool-Calling AI Agent**。

v6 相对 v5 的变化（按主题）：

| 主题 | v5 状态 | v6 状态 |
|---|---|---|
| Redis | 只有短信验证码在用，`cache_conf` 是死代码 | 博客列表/详情缓存 + 互斥锁回源 + 分布式锁 + HLL UV |
| 评论 | 无 | 楼中楼评论（软删 + 归属鉴权） |
| 手机号 | 实验性、待加 `phone` 字段 | 双列加密存储（`phone_encrypted` / `phone_hash`）+ 手机号注册 |
| 短信 | mock，实验性 | mock 保留（个人资质限制），接口契约已完成 |
| 限流 | 无 | AI 接口按用户限流 + 短信失败锁定 |
| 安全 | — | 删除硬编码 API Key、Redis 密码（**部分未落地，见 §13**） |

### v6.1 变更记录（2026-09-15）：「编辑已发布文章」闭环

版本主题：把 v6 已建好的接口接上"最后一公里"。后端改动很小（前端为主），核心是 `PUT /update` 从"只能改标题正文"升级为"支持改标签"：

| 改动 | 位置 | 说明 |
|---|---|---|
| `BlogUpdate` 补 `tag_ids` / `tag_names` 可选字段 | `schemas/blogs.py` | 二者至少传其一；都传则取并集。**前端统一提交 `tag_names`**（标签不存在时自动新建，与发文同逻辑） |
| 标签解析抽公共函数 `_resolve_tag_ids()` | `curd/blogs.py` | 「存在取 id，不存在新建」，`add_blog` / `update_blog` 共用；解析放在删除旧关联**之前**（先 flush 新 tag 再删旧关联，避免主键冲突） |
| `update_blog` 支持标签重绑 | `curd/blogs.py` | 「删旧 + 插新」全量替换（不做增量 diff，天然幂等）。两个关键守卫：① 标签字段必须先从 `model_dump()` 结果里 `pop` 出来再进 `.values()`，否则报 `no such column`；② 重绑条件是 `tag_ids is not None or tag_names is not None`——**显式传 `[]` 表示清空标签**，写成 `if tag_ids:` 会吞掉这个语义 |
| `get_blog_detail` 补传 `create_time` | `curd/blogs.py` | 修复详情页日期一直显示"未知日期"的隐藏 bug（`BlogResponse` 有字段但构造时没传） |

配套前端（`fontend/`，由 AI 直接修改）：详情页作者操作区（编辑/删除按钮，按 `user_id` 判 `isOwner`，修复了原来任何登录用户都能看到删除按钮的权限误展示）、`/write?edit=<id>` 编辑模式（原文回填 + `updatePost`）、标签统一走 `tag_names`（修复原 `TAG_MAP` 过滤静默丢弃自定义标签的 bug）。⚠️ 注意 **`/posts/:id` 和 `/write` 实际渲染的是 `HomePage.vue`**，`views/BlogDetail.vue`、`views/EditorPage.vue` 是无引用的死代码（待删，勿在其上继续开发）。

### 技术栈

| 领域 | 选型 |
|---|---|
| Web 框架 | FastAPI（ASGI，`main.py`） |
| ORM | SQLAlchemy 2.0（`Mapped` / `mapped_column`，异步 `AsyncSession`） |
| 数据库驱动 | `asyncmy` |
| 关系型数据库 | MySQL 8.0 / 8.4 |
| 缓存 / 计数 | Redis 7（redis-py `asyncio` 客户端，单例在 `config/cache_conf.py`）；HLL 用于 UV |
| 认证 | JWT（PyJWT，HS256）+ HTTPBearer；`utils/jwt.py` 签发、`utils/auth.py` 校验 |
| 密码哈希 | bcrypt（passlib，锁 `bcrypt==4.0.1`，5.x 与 passlib 1.7.4 不兼容） |
| 对称加密 | Fernet（`utils/crypto_utils.py`，密钥走 `PHONE_ENCRYPTION_KEY`） |
| LLM / Agent | LangChain + 阿里云百炼（ChatTongyi / TextEmbedding） |
| 向量库 | Chroma（本地持久化 `./chroma_data`） |
| 流式输出 | SSE（`text/event-stream`） |
| 运行时 | uvicorn；容器经 `docker_entrypoint.sh` → `docker_start.py` 拉起 |

### 分层架构

```
请求 → Router(routers/) → Service(services/) / curd/
        → Model(models/) + Schema(schemas/) 校验
        → 数据库(AsyncSession, db_conf) / 缓存(Redis, cache_conf)
AI 链路：Router(ai.py) → AgentService → LLM 抽象层(llm/) + Tool 注册表(tools/)
RAG 链路：ingest(retrieve/embeddings/store) → Chroma
```

两条硬约定（v6 起明确）：

1. **路由层只做编排**：收请求 → 调 service/curd → 返回响应。纯转换逻辑下沉到 `services/`（如 `rss_service.py` 生成 RSS、`blog_cache.py` 管缓存键），不在 `routers/*.py` 里定义业务函数。
2. **增强功能必须可降级**：RAG / Redis / Agent 异常一律吞掉或返回兜底，绝不影响核心发文读文链路（见 `services/blog_rag.py` 的 `_safe_ingest` / `_safe_remove`，以及 `cache_conf.py` 各函数的 `try/except` 返回 `None`）。

## 3. 数据模型

基类在 `config/base.py`：`Base`（`DeclarativeBase`）、`time_Base(Base)`（自动附加 `create_time` / `update_time`）。

### 实体关系

```
┌─────────┐       ┌──────────┐       ┌─────────┐
│  user   │ 1   * │  blog    │ *   * │   tag   │
└─────────┘       └────┬─────┘       └─────────┘
                       │ 1
                       │ *
                  ┌────┴─────┐
                  │ comment  │  self-ref parent_id（楼中楼）
                  └──────────┘

  music(id, title, artist, cover, src)          -- 音乐播放列表
  chat_history(id, user_id, role, content)      -- AI 对话历史
```

### 关键模型字段

| 表 | 字段 | 说明 |
|---|---|---|
| `user` | id, username(uniq), password, **phone_encrypted**, **phone_hash**(uniq), **nickname**, **avatar**, **bio**, is_delete | 密码 bcrypt；手机号双列：Fernet 可逆加密 + HMAC-SHA256 哈希（查重/定位） |
| `blog` | id, title, content(Text), user_id(FK→user.id), is_delete, create_time/update_time | 软删除 |
| `tag` | id, name(uniq), is_delete | 种子 6 条：Python/AI/Vue/FastAPI/Docker/其他 |
| `blog_tag` | id, blog_id(FK), tag_id(FK) | 多对多，unique(blog_id, tag_id) |
| `comment` | id, blog_id(FK), user_id(FK), content(Text), **parent_id**(self FK，楼中楼), is_delete | 软删除；删除校验归属（非作者 403） |
| `music` | id, title, artist, cover(nullable), src | 前端播放器数据源 |
| `chat_history` | id, user_id(index), role(`user`/`assistant`), content(Text) | AI 对话持久化 |

> 生产库同步：v6 上线时用 `ALTER TABLE user ADD COLUMN ...` 补了 5 列 + `uk_phone_hash` 唯一索引（MySQL 8.4 为 INSTANT DDL），详见 `docs/v6-release-notes.md` §五。

## 6. API 接口文档

统一响应封装（`utils/response.py`）：
- 成功：`{"code":200, "message":"...", "data":...}`

全局：`GET /health` 返回 `{status, db, redis}`（任一不可用为 `degraded` + 503）。

## 7. 认证机制

- **签发**：`utils/jwt.py` 的 `create_access_token({"sub": str(user_id)})`，HS256，3 天有效。密码登录与短信登录共用。
- **校验**：`utils/auth.py` 的 `get_current_user`，依赖 `HTTPBearer`，从 `Authorization: Bearer <token>` 取 token → 解码 → 查库确认用户存在。
- **密码**：`utils/security.py`，passlib bcrypt，>72 字节先截断。
- **手机号**：`utils/crypto_utils.py` 提供 Fernet 加解密与 HMAC-SHA256 哈希（`hash_value`）。

## 8. Redis：缓存与高并发（v6 新增）

**连接单例**在 `config/cache_conf.py`（`redis.asyncio` 客户端，**所有命令必须 `await`**），对外只暴露语义化函数：`get_cache / get_json_cache / set_cache / delete_cache / clear_prefix`，全部带 `try/except` 兜底（Redis 挂了不 500）。缓存策略常量也集中在此：

| 常量 | 值 | 用途 |
|---|---|---|
| `DEFAULT_CACHE_TTL` | 600s | 基础 TTL |
| `CACHE_TTL_JITTER` | 300s | 随机抖动，防雪崩 |
| `PENETRATION_TTL` | 60s | 空结果（哨兵）TTL，防穿透 |
| `NONE_SENTINEL` | `{"__none__": True}` | 空结果哨兵（dict 形式，保证 `json.loads` 可解析） |

**业务缓存**在 `services/blog_cache.py`，key 前缀统一：`blog:list:` / `blog:detail:`。路由只调语义函数，不碰裸 key 与 TTL。

**防击穿（互斥锁回源）** `get_blog_detail_with_mutex`：
- 只有抢到锁的协程才查 DB 写缓存；等待者自旋到锁消失后**只读缓存，永不查 DB**
- 自旋总时长需 ≥ 锁 TTL，否则等待者提前 fall through 打穿 MySQL
- 空结果写 `NONE` 哨兵，短期不再回源

**分布式锁** `services/redis_lock.py`：`SET NX EX` + 唯一 token + Lua 脚本防误删 + 看门狗续期；`RedisLockCtx` 为 `async with` 形式，已用于发文防重复提交。

**UV** `services/uv_service.py`：HyperLogLog `pfadd / pfcount`，key `uv:blog:{id}`、`uv:site:all`，误差约 0.81%，只看趋势。

**限流** `services/ratelimit_service.py`：`ai_rate_limited(user_id)` 用于 `/api/ai/chat`；`sms_is_locked / sms_record_fail` 用于短信防暴破。

> ⚠️ 任何新代码需要 Redis 时，必须 `from config.cache_conf import redis_client` 或复用上述语义函数，**禁止自建 `redis.Redis(...)`**——否则绕过连接池与测试隔离（`tests/conftest.py` 的 `redis_isolated` fixture）。

## 9. RAG 博客问答系统

目录 `rag/`：

| 层 | 文件 | 职责 |
|---|---|---|
| L1 向量化 | `embeddings.py` | `qwen3.7-text-embedding`，**1024 维、已 L2 归一化**；`_BATCH_SIZE=8` 分批防限流 |
| L2 向量存储 | `store.py` | Chroma `PersistentClient(path="./chroma_data")`，集合 `blog_chunks`，`hnsw:space=cosine`；`add_chunks` 用 upsert |
| L3 入库 | `ingest.py` | `split_text`（块 500 字 / 重叠 50 字）；`ingest_all`（过滤正文 <50 字噪声）、`ingest_one`（增量 upsert）、`remove_one`（按 `post_id` 删 chunk） |
| L4 检索 | `retrieve.py` | 向量化 → `query(top_k=3)` → `STM_THRESHOLD=0.85` 余弦距离过滤 → 拼 `context` + `citations`；另有 `should_retrieve` 判定是否需要检索 |

**业务同步**（`services/blog_rag.py`，v5 时为 `blog_service.py`）：
```
POST /add     → create_blog_with_rag → 写库 → _safe_ingest → ingest_one
PUT  /update  → update_blog_with_rag → 写库 → upsert 向量
DELETE /delete→ delete_blog_with_rag → 软删 → _safe_remove → remove_one
```
RAG 失败只记日志，不影响业务返回——刻意设计的容错边界。

首次部署需初始化向量库：
```bash
docker compose run --rm backend python -c "import asyncio; from rag.ingest import ingest_all; asyncio.run(ingest_all())"
```

## 11. Docker 启动流程

1. `docker_entrypoint.sh`：修正 `chroma_data` / `uploads` 卷属主 → 降权到 `appuser`(uid 1000) 执行 `docker_start.py`（用 `setpriv` 使 uvicorn 成为 PID 1，保证 SIGTERM 优雅退出）。

3. 健康检查：`GET /health`（同时探 DB 与 Redis）。
